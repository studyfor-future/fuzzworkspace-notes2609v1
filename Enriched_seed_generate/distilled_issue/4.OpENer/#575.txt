Number: 575

Summarize:
OpENer v2.3 / master branch up to commit 76b95cf has a remotely reachable stack-use-after-return in the EtherNet/IP Common Packet Format (CPF) handling logic. The process-global CPF parsing state `g_common_packet_format_data_item` is reused across messages and protocol paths; `CreateCommonPacketFormatStructure()` only refreshes `data_item` when `item_count >= 2`, so a later CPF packet with `item_count == 1` updates only the address item and leaves the previous `data_item.type_id`, `data_item.length`, and `data_item.data` unchanged. A valid UDP I/O consuming packet can therefore populate `g_common_packet_format_data_item.data_item.data` with a pointer into the stack buffer of `CheckAndHandleConsumingUdpSocket()`, and a later TCP `SendUnitData` packet with only a `ConnectionAddress` item can reuse that stale UDP `data_item` in the TCP connected explicit path, causing `NotifyConnectedCommonPacketFormat()` to read from a returned UDP stack frame. The documented result on ASan builds is an `AddressSanitizer: stack-use-after-return` crash in `GetUintFromMessage`; the report states this is at minimum a remotely triggerable denial of service.

Reproduce:
Use the unmodified POSIX OpENer server from v2.3 / master up to commit `76b95cf`; for the shown diagnostic, use an ASan build. Save the provided Python 3 PoC as `poc.py` and run the documented example: `python3 poc.py udp_to_tcp 192.168.153.128 494`. The PoC connects to TCP port 44818, sends `RegisterSession`, then sends two `ForwardOpen` requests via `SendRRData` to establish an I/O connection and a Class 3 connection and collect their returned connection IDs. In `udp_to_tcp` mode it first sends a normal TCP connected explicit `SendUnitData` `GET_VENDOR_ID` request to prime the Class 3 sequence counter, then sends a UDP connected packet to port 2222 with `item_count=2`, a sequenced-address item, and a `0x00B1` data item of length 494 to seed the global CPF `data_item` from the UDP stack buffer. It then sends a TCP `SendUnitData` packet with `item_count=1` and only the `ConnectionAddress` item, which causes the stale UDP `data_item` to be reused in the TCP connected explicit path. Expected result: the server reports `AddressSanitizer: stack-use-after-return`; the trace shown starts at `GetUintFromMessage` (`source/src/enet_encap/endianconv.c:75`), then `NotifyConnectedCommonPacketFormat` (`source/src/enet_encap/cpf.c:141`), `HandleReceivedSendUnitDataCommand`, `HandleReceivedExplictTcpData`, `HandleDataOnTcpSocket`, `NetworkHandlerProcessCyclic`, and `main`.
