Number: 1399

Summarize:
In bacnet-stack 1.5.0 (master branch commit 932e347), the RAMFS-backed FILE object implementation mismatches appended record storage and record counting. `handler_atomic_write_file_encode()` treats `FILE_RECORD_ACCESS` with `fileStartRecord == -1` as append and routes it through `bacfile_write_record_data()` / `bacfile_write_record_data_callback()` to `bacfile_ramfs_write_record_data()`. The append path allocates only the record bytes plus a terminating NUL, but `record_count()` later walks the buffer as if an additional empty-record sentinel exists. After one NUL-terminated record is present, a second consecutive AtomicWriteFile append to the same writable FILE object causes `record_count()` to advance to the end of the heap allocation and call `bacnet_strnlen()` (implemented with `memchr`) on a pointer one byte past it, producing an out-of-bounds heap read. The report explicitly says this is remotely reachable through the normal BACnet AtomicWriteFile service path; the observed behavior is the OOB read, while crash, denial of service, or other undefined behavior are described as possible outcomes.

Reproduce:
The document does not include build instructions. Prerequisite: an affected target exposing a writable RAMFS-backed `OBJECT_FILE`; the PoC uses file instance `1`. The provided client takes `<device-instance> <file-instance>`; the source shows example arguments `260001 1`. Steps: 1) start the client, initialize BACnet handlers, send `Who-Is`, and wait until the target device is bound; 2) send `AtomicWriteFile(OBJECT_FILE, 1, FILE_RECORD_ACCESS, fileStartRecord = -1, returnedRecordCount = 1, fileData[0] = "AAAA")` and wait for the ack; the report says this creates a 5-byte heap buffer containing `AAAA` plus a terminating NUL; 3) send `AtomicWriteFile(OBJECT_FILE, 1, FILE_RECORD_ACCESS, fileStartRecord = -1, returnedRecordCount = 1, fileData[0] = "BBBB")` to the same file. Expected result: before the second record is appended, the server re-enters `bacfile_ramfs_write_record_data()`, `record_count(pFile->data)` advances exactly to the end of that 5-byte allocation, and `bacnet_strnlen()` is called on a pointer already one byte past it, triggering the reported out-of-bounds heap read.
