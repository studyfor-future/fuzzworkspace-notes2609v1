Number: 568

Summarize:
OpENer 2.3.0 (master branch up to commit 76b95cf) has an integer underflow in the connected explicit message path for SendUnitData. In `source/src/enet_encap/cpf.c`, `NotifyConnectedCommonPacketFormat` subtracts 2 from the connected data-item length without checking that it is at least 2; a length of 1 underflows to -1. That value is passed into `CreateMessageRouterRequestStructure` in `source/src/cip/cipmessagerouter.c`, decremented again, and later bypasses a bounds check because the signed length is compared after an implicit unsigned conversion. With a forged large `path_size`, `DecodePaddedEPath` can read far out of bounds from the `incoming_message` buffer, which the report describes as a stack buffer overflow and severe memory corruption.

Reproduce:
Use the provided Python TCP client against the target host and port 44818 (default host 127.0.0.1). Each request uses a 24-byte header: `<HHII` command, payload length, session, 0, plus 12 null bytes. Connect with a 2s timeout; send Register Session (0x65) with payload `struct.pack('<HH', 1, 0)` and read the session ID from bytes 4-7 of the reply; send ForwardOpen (0x6F) on that session with the provided CIP/CPF bytes, then extract the connection ID from the reply at marker `\xD4\x00\x00\x00`; finally send SendUnitData (0x70) on the same session with CPF item `0x00A1`, that connection ID, and a connected data item `0x00B1` whose length is `1`, followed by one null byte and the forged path tail `\x41\x0e\xfa` plus `\x20\x02` repeated 232 times. The write-up says the trigger should hit the bug; if ASAN catches it, OpENer crashes.
