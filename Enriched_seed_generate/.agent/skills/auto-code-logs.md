# Skill: auto-code-logs

## 1. 本文件的作用：路径约束

本 Skill 的核心职责不是“怎么写日志”，而是 **把三类日志约束到固定的目录结构里**，并保证：
- 所有日志 **只能** 写在「配置区」定义的 `LOG_ROOT` 之下；
- 一级子目录 = 日期，二级子目录 = 类别，命名规则固定；
- 同名/同类别/同日期冲突时，通过文件名时间戳或目录名关键词区分，绝不覆盖既有内容；
- 每次阶段性任务结束都必须落一条记录（默认开启），由 Agent 自动判断类别并写入/追加，无需用户每次手动要求。

> 路径约束优先级：**用户本次显式指定的路径 > 配置区 `LOG_ROOT` > 默认值**。

## 2. 默认行为

- **默认开启**：只要正在进行代码类任务（修改、测试、正式运行），Agent 在本阶段结束、汇报给用户之前，必须先完成本次日志记录。
- 日志按 **三类独立类别** 组织：
  1. **code_plan** — 代码修改计划过程日志（计划安排 + 具体执行）；
  2. **code_test** — 代码测试过程日志（测试结果 + 错因分析）；
  3. **code_run** — 代码正式运行过程日志（运行过程 + 结果）。
- 一次任务往往跨越多个类别：计划阶段写 `code_plan`，验证阶段写 `code_test`，最终交付/跑正式流程写 `code_run`。每个阶段结束各记一条（或补充到同一任务文件，见 §7 追加规则）。

## 3. 【可配置区】（明文代码区域，人工修改）

改这里即可全局改变路径与命名。**路径变量是本 Skill 唯一的路径来源，Agent 不得在正文中自行另设其他输出路径。**

```text
# ===== 可配置区（Path Constraint Config）=====
# 项目根：自动取包含 README.md / config.py 的目录；若无法识别则由用户指定。
# Enriched Seed Generation 项目统一采用 docs/logs 模式（参考 docs/logs/260906）。
# 这是本项目的唯一日志根目录，路径一律以此为准。
LOG_ROOT      = {project_root}/docs/logs/

# 日期一级目录格式：%y%m%d -> 260907（与仓库现有 docs/logs/260906 一致）
# 如需完整年份可改为 %Y%m%d -> 20260907
DATE_FORMAT   = %y%m%d
# 文件名内嵌时间戳
FILE_STAMP    = %Y%m%d_%H%M%S

# 三类日志的类别目录关键词（英文，固定）
CATEGORIES    = code_plan | code_test | code_run
# 类别目录无法区分任务时，追加关键词的分隔符（见 §5 规则4）
SUFFIX_SEP    = _
# 开关：默认开启。置为 off 时仍需保留最近一条未落盘日志的路径提示。
LOGGING_ON    = on
# ===== 可配置区结束 =====
```

对应到本项目，默认展开即：

```text
E:\workspace\fuzzv1\tools\Enriched_seed_generate\docs\logs\
```

## 4. 目录结构规则

```
<LOG_ROOT>/                          # 例如 docs/logs/
└── <DATE>/                          # 一级：日期，如 260907（格式见配置区）
    ├── code_plan/                   # 二级：类别1 代码修改计划过程
    │   └── <类别>_<任务关键词>_<文件戳>.md
    ├── code_test/                   # 二级：类别2 代码测试过程
    │   └── <类别>_<任务关键词>_<文件戳>.md
    └── code_run/                    # 二级：类别3 代码正式运行过程
        └── <类别>_<任务关键词>_<文件戳>.md
```

命名补充规则：
- 类别目录使用固定英文关键词：`code_plan` / `code_test` / `code_run`；
- 文件名由 `类别关键词 + 任务关键词 + 时间戳` 组成（如 `code_plan_2x2-ablation_20260907_143022.md`），保证同一目录内不重名；
- 与仓库历史参考（如 `docs/logs/260906/01_VK_ONLY_IMPLEMENTATION_LOG.md`）保持一致：日期目录用紧凑年月，文件可带数字序号前缀 `NN_` 便于顺序阅读。

## 5. 记录规则（重点：防止日志乱放）

1. **先算路径，再写内容**：写任何日志前先计算目标绝对路径；路径必须以 `LOG_ROOT` 开头，否则视为越界，应修正而非写入。
2. **目录不存在则创建**（`mkdir -p`），父目录一路建齐。
3. **日期目录**：取“本阶段任务结束当天”的本地日期，用配置区 `DATE_FORMAT` 格式化。
4. **类别目录无法区分 / 需要隔离多个并行任务时加关键词**：
   - 同一日期、同一类别下存在多个相互独立的任务线程时，在子目录上追加任务关键词，如：
     `docs/logs/260907/code_plan_2x2-ablation/` 与 `docs/logs/260907/code_plan_refactor/`；
   - 若日期也无法区分任务（跨日任务、补录），在日期目录上追加关键词：`260907_2x2-ablation/`。
5. **新任务 → 新文件；同一任务的后续阶段/补充 → 追加到原文件**（新增带新时间戳的小节），绝不整文件覆盖既有内容。
6. **写入后向用户汇报一次相对路径**（相对项目根），例如：
   `已记录 → docs/logs/260907/code_plan/code_plan_2x2-ablation_20260907_143022.md`

## 6. 三类日志内容定义

### 6.1 类别1 — 代码修改计划过程日志 `code_plan`

记录“这次改动”从计划到落地的全过程。字段（模板块见 §6.4）：

| 部分 | 必含内容 |
|---|---|
| 计划安排 | 任务背景、目标、拟改文件/函数/模块、分步计划、预期影响、向后兼容性要求 |
| 具体执行 | 实际改动的文件与函数、新增/删除/替换的逻辑、关键 diff 摘要、遗留 TODO |
| 结果小结 | 本次改动是否落地、与计划的偏差 |

### 6.2 类别2 — 代码测试过程日志 `code_test`

记录验证阶段的客观事实与错因分析：

| 部分 | 必含内容 |
|---|---|
| 测试信息 | 被测版本/文件、测试命令与参数、测试范围（用例数） |
| 测试结果 | 通过/失败、失败用例清单、输出/报错原文摘录 |
| 错因分析 | 根因推断、定位到的代码位置、修复建议或已做修复 |
| 结论 | 是否可进入正式运行 |

### 6.3 类别3 — 代码正式运行过程日志 `code_run`

记录真实运行（非测试）过程：

| 部分 | 必含内容 |
|---|---|
| 运行环境 | 主机、Python/依赖版本、API 通道/模型、关键环境变量（不含密钥明文） |
| 启动命令 | 实际执行的完整命令行（如 `python Generate.py --format ... --functions ...`） |
| 关键输出 | 运行日志要点、产物路径、耗时/规模等可量化指标 |
| 运行状态 | 成功 / 异常；异常时给出错误信息与影响范围 |

### 6.4 通用 Markdown 模板

三类共用同一骨架，正文按类别替换：

```markdown
# <类别中文名>

- Date: <YYYY-MM-DD HH:MM:SS>
- Category: <code_plan|code_test|code_run>
- Task: <任务关键词，如 2x2-ablation>
- Related file(s): `<相对路径>`（如 `Generate copy.py`）
- Status: <planned | done | in-progress | passed | failed | succeeded | abnormal>

## <按类别填写，见 §6.1–6.3>

## 追加小节（多次记录时按时间追加）
### <YYYY-MM-DD HH:MM:SS> <阶段名>
...
```

## 7. 记录时机（默认开启的触发点）

以下任一时间点到达，Agent 必须先落日志（或补充到既有同任务文件），再向用户汇报：

1. 代码**计划确定**或**修改执行完毕**时 → `code_plan`；
2. **测试执行结束**（无论通过与否）→ `code_test`；失败必须含错因分析；
3. 代码**正式运行开始/结束** → `code_run`；运行被中断也要记录中断点；
4. 用户明确说“记录一下 / 写日志 / 存档 / 更新 changelog”等 → 立即记录；
5. 一段多轮工作被中断、或上下文将要结束时 → 用当前已知信息补充最近一条日志，避免丢档。

若一次结束时同时包含多个类别（如“改完并测过”），则分别写入 `code_plan` 与 `code_test` 两条（或两条路径都指向同一任务文件时按 §5 规则分别落不同类别目录）。

## 8. 内容生成来源

日志正文由 Agent 自动生成，优先顺序：

1. **本次聊天记录**：任务目标、用户的决定、我给出的方案与理由、遇到的报错与修复；
2. **项目文件对比**：改动前后对比（`git diff`；无 git 时对比同目录备份/副本，如本项目 `Generate copy.py` vs `Generate.py`）、测试输出文件、运行产物/`manifest.json`；
3. **客观化**：可量化处写具体数字/路径/命令；推断性内容（如根因）标注为“推断”，事实与推断分离，不编造测试或运行结果。

禁止：写入 API Key 等明文密钥、任何第三方机密；确需记录环境时用“<KEY 已注入>”占位。

## 9. 写入约束与边界

- 不创建 LOG_ROOT 之外的日志/备份文件；
- 不删除、不重写他人的日志；同任务补充一律新增小节，保留历史；
- 日期取本地当天；跨日续写旧任务时，新小节落在**原文件**并标注新时间，不另开日期目录硬拆；
- 无法判定类别且不值得询问时，默认归 `code_plan`，并在文件首部注明“类别由 Agent 默认判定”。

## 10. 完成反馈

每次落盘后，向用户回复一行确认，格式：
`已记录 <类别中文名> → <相对路径>（若为追加：第 N 小节）`。

## 11. 与本项目参考的一致性

- 现有日志参考：`docs/logs/260906/*.md`、`docs/logs/260906/2x2-all-protocols-raw-20260906/{REPORT,ERROR_PROCESS}.md`；
- 本 Skill 约定的类别二级目录 `code_plan/code_test/code_run` 是相对参考日志**新增的结构化约束**，用于把参考中混合的“实现/报错/报告”内容分门别类；
- 日期目录沿用仓库紧凑格式 `YYMMDD`（260906 → 260907）。
