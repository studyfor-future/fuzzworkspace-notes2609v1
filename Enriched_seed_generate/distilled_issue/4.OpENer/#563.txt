Number: 563

Summarize:
OpENer 2.3.0 (commit 76b95cf) is reported vulnerable during incoming CIP packet parsing because `source/src/cip/cipmessagerouter.c` uses inconsistent length types and missing bounds checks: `NotifyMessageRouter(..., int data_length, ...)` passes the length to `CreateMessageRouterRequestStructure(..., EipInt16 data_length, ...)`. The report says crafted length fields can make the value negative, bypass the `if(number_of_decoded_bytes > data_length)` check, and underflow `request_data_size = data_length - number_of_decoded_bytes` before the value reaches `DecodePaddedEPath`. The supplied PoC sends crafted CIP traffic, including a `SendUnitData` packet with `ITEM_CONN_DATA` length `1`, and the shown output reports a runtime error in `source/src/enet_encap/endianconv.c:101` followed by an AddressSanitizer stack-buffer-overflow read in `DecodePaddedEPath` that overruns the stack `incoming_message` buffer and aborts.

Reproduce:
Run the provided Python PoC against an OpENer 2.3.0 (commit 76b95cf) POSIX run instrumented as shown in the `ASan` section; the PoC defaults are `--host 127.0.0.1 --port 44818 --attempts 5 --timeout 1.5`. For each attempt, the client opens a TCP connection, sends `RegisterSession`, sends `SendRRData` with a UCMM `Forward Open` request, parses the response, and extracts the returned consumed connection ID. It then sends `SendUnitData` with three CPF items: `ITEM_CONN_ADDR` containing that connection ID, `ITEM_CONN_DATA` with length `1` and payload `0x00`, and a crafted tail of `512 - 45` bytes (the PoC comment says this aligns with the default receive buffer size) starting with `0x41, 0x0E, 250` and then repeated `0x20 0x02` bytes; the loop repeats up to 5 times with 0.15 s delays. Expected result: the PoC may report `trigger sent, no response (possible crash)` or a response length, and the instrumented server prints `runtime error: left shift of 128 by 24 places cannot be represented in type 'int'`, `something is wrong with the length in Message Router @ CreateCommonPacketFormatStructure`, then `ERROR: AddressSanitizer: stack-buffer-overflow` in `DecodePaddedEPath`, showing the read overruns the stack `incoming_message` buffer and the process aborts.
