Number: 599

Summarize:
On branches v1.6_develop and v1.6, client-side handling of GetNamedVariableListAttributesResponse is vulnerable because parseNamedVariableAttributes(...) accepts a remote domain-specific itemId without validating that it has the expected IEC 61850 $FC$... suffix. When IedConnection_getDataSetDirectory(...) later passes that value to MmsMapping_varAccessSpecToObjectReference(...), the mapper assumes an internal LN$FC$... layout and performs fixed-offset reads after the first '$'. If a malicious MMS server, or an active MITM modifying a legitimate response, reduces the first itemId to "$", the function reads past the 2-byte heap string and libIEC61850 client applications can crash with an AddressSanitizer-detectable heap-buffer-overflow read through the normal protocol state machine.

Reproduce:
Use the documented artifacts: the official server at ./build-debug/examples/server_example_basic_io/server_example_basic_io, the official client at ./build-asan/examples/iec61850_client_example2/iec61850_client_example2, and the supplied Python3 transparent TPKT proxy PoC. The proxy forwards traffic between client and server, but for the first real GetNamedVariableListAttributesResponse it rewrites the first domain-specific itemId TLV to the single-byte string "$" and updates the BER and TPKT lengths. Steps: (1) Terminal 1: ./build-debug/examples/server_example_basic_io/server_example_basic_io 18171. (2) Terminal 2: python3 proxy.py --listen-port 28177 --target-port 18171 --verbose. (3) Terminal 3: ./build-asan/examples/iec61850_client_example2/iec61850_client_example2 127.0.0.1 28177. Expected result: the proxy reports that it patched the first GetNamedVariableListAttributesResponse, for example "[proxy] patched first GetNamedVariableListAttributesResponse new_tpkt_len=210", and the ASan-built client then hits a heap-buffer-overflow read and crashes while converting the malformed dataset entry to an IEC 61850 object reference.
