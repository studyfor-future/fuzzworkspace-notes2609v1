Number: 565

Summarize:
OpENer commit 76b95cf is reported to have incorrect access control in encapsulation-session handling. In encap.c, CheckRegisteredSessions() checks whether a supplied session_handle is active in the global session list, but not whether that handle belongs to the TCP socket that sent the request. The report says this weak check is used on critical command paths such as SendRRData and SendUnitData, and that UnregisterSession also tears down session resources based only on the handle. A request sent on one connection with another client's valid session_handle can therefore pass session validation. The provided observations show the attacker PoC enumerating/using a valid victim handle, then sending a forged UnregisterSession that the server accepts, destroying the session and forcefully closing the legitimate client's TCP socket. The report also describes this as session hijacking and cross-connection DoS; the demonstrated result shown is the forced disconnect of the legitimate client.

Reproduce:
Use an OpENer target at commit 76b95cf; the document does not provide server build commands. Have a legitimate client already connected with an active encapsulation session; the report names the normal client as normal_client.py. Run the provided Python attacker PoC against the ENIP listener (defaults: --host 127.0.0.1, --port 44818, --timeout 1.5). If the victim session handle is known, pass --victim-session <handle>; otherwise let the script probe 1..--max-handle (default 20). The attacker connects, can optionally call RegisterSession on its own socket (--register-attacker), and then probes candidate handles by sending SendRRData with a benign Get_Attributes_All CIP payload. Any response whose ENIP status is not 0x0064 (invalid session handle) is treated as proof that the handle exists and is accepted on the attacker socket. After discovering such handle(s), leave default unregister behavior enabled (do not use --no-unregister) so the attacker sends UnregisterSession for the victim handle(s) from the wrong TCP connection. Optional --asan-rounds with --route-path-len repeatedly sends oversized ForwardClose route-path payloads over hijacked handles. Expected observations: the attacker terminal reports accepted/hijackable handles and sent unregister messages; server logs show the forged unregister being processed, the session destroyed, and the legitimate client's socket being closed; the legitimate client immediately reports "DISCONNECTED: connection closed/no response".
