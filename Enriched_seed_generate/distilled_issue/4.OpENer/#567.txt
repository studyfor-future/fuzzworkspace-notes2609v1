Summarize:
On the latest master branch of OpENer, the report describes a remotely reachable server-side crash triggered by a crafted EtherNet/IP SendRRData request. The report attributes the underlying corruption to request handling before the visible crash: CreateCommonPacketFormatStructure() accepts a malformed CPF with an invalid item_count/inconsistent length, the unconnected Message Router payload reaches GetAttributeList(), GetAttributeList() parses an attacker-controlled excessively large attribute_count_request and builds an oversized inner Message Router response, and EncodeMessageRouterResponseData() copies that inner response into the outer ENIPMessage without validating remaining destination capacity. According to the report, this overruns message_buffer[512] and overwrites the adjacent current_message_position field; the observed result is that AddIntToMessage() later dereferences the corrupted pointer and crashes. The documented crash is an AddressSanitizer SEGV caused by a READ in AddIntToMessage() at source/src/enet_encap/endianconv.c:136.

Reproduce:
1) Use the latest master branch of OpENer and run a server instance; the report demonstrates the issue on an AddressSanitizer-instrumented POSIX OpENer build. 2) Send the provided crafted EtherNet/IP SendRRData request to the server. The PoC is the hex byte sequence beginning with <6f><00><30><01><30><30><30><30> and continuing exactly as provided in the document. 3) Observe the server abort under AddressSanitizer with a SEGV caused by a READ in AddIntToMessage() at source/src/enet_encap/endianconv.c:136:49, with the stack including EncodeSockaddrInfoItemTypeId(), AssembleLinearMessage(), NotifyCommonPacketFormat(), HandleReceivedSendRequestResponseDataCommand(), and HandleReceivedExplictTcpData().
